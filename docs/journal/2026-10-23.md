# 2026-10-23

Six faults found while bringing the desktop up to the Ryoku shell it was ported from. None
of them crashed anything: each showed up as a thing that was missing or did nothing.

## The bar was empty: the package left out what the entry point imports

**Symptom.** A login that reached a compositor with no bar, no dock and no launcher.

**Cause.** `release/build-debs.sh` copied the shell's directories from a hand-written list,
and the list stopped where the tree had stopped growing. The package installed the new
`shell.qml` without `Services/` or `Ui/`, the directories it imports as `qs.Services` and
`qs.Ui.Singletons`, so Quickshell had nothing to draw.

**Fix.** The shell tree is laid down whole, with the few checkout-only files named as
exclusions (`6314ce4`), and the release test asserts that every file of the shipped tree
lands byte-identical. `tests/contract/load.sh` loads a tree in a sandbox with no display and
fails on a module that does not resolve, so a package can be checked before it is installed.

**Evidence.** `journalctl --user -u zenith-shell`, 17:03:46 on 2026-10-23:
`caused by @shell.qml[13:1]: module "qs.Services" is not installed` and
`caused by @shell.qml[33:1]: module "qs.Ui.Singletons" is not installed`. The header of
`load.sh` records that a copy of the tree with `Services/` deleted logs the first line and
the whole tree logs only the expected `No PanelWindow backend loaded`.

## There was no daemon: every service that talks to one failed to connect

**Symptom.** The services that front the daemon (tray, network, power profiles, clipboard,
weather, updates) had nothing to show, and the shell's journal was full of socket warnings.

**Cause.** The shell's services connect to `$XDG_RUNTIME_DIR/zenith-shell.sock`, and nothing
listened. `docs/architecture.md` described a state daemon, `zenithd`, as if it existed. It
had never been built: the package shipped `/usr/bin/zenith` and the `/usr/bin/zenith-hub`
launcher, and no daemon.

**Fix.** `zenith-shell daemon`, ported from Ryoku's `ryoku-shell` and run by
`zenithd.service`; the docs now say so. Ordering is the trap. This Quickshell build fires no
signal when a first `Socket` connect fails, so a service that connected before the daemon
bound its socket never retries, and the shell has to start after the daemon has the socket
(`docs/session.md`).

**Evidence.** 3558 `QLocalSocket::ServerNotFoundError` warnings from `zenith-shell` in the
boot that began at 16:52 on 2026-10-23, counted that evening. `dpkg -L zenith` lists
`/usr/bin/zenith` and `/usr/bin/zenith-hub` and no daemon.

## Super+Tab opened the window switcher and closed it in the same instant

**Symptom.** Super+Tab showed the switcher card for about 50 ms, as reported, which reads as
nothing happening. The request was that Super+Tab should show the windows.

**Cause.** The configuration opened the card with `bind = SUPER, Tab` and closed it with
`bindl = SUPER, Tab`. In Hyprland the `l` flag means *locked* (the bind also works while the
session is locked), not "release". Both binds fire on the press.

**Fix.** Super+Tab opens the workspace overview and Super+Alt+Tab steps its desktops. Alt+Tab
is the most-recently-used switcher, its release is `bindr`, and the card stays up for 450 ms
after the last press. The header of `session/hyprland/binds.conf` records which flag means
what.

**Evidence.** The pair at lines 60-61 of `session/hyprland/hyprland.conf` at `HEAD`, and the
`l` and `r` flags in Hyprland's binds documentation.

## Opening any secondary window killed every keybind that calls the shell

**Symptom.** With Settings, the screenshot tool or the wallpaper picker open, the launcher
and every other shell bind did nothing until the window was closed.

**Cause.** The binds go through `zenith ipc`, which finds the running shell by listing
`quickshell` processes and refuses to guess between two. Each secondary window is a
`quickshell -p .../ENTRY.qml` process of its own, so one open window made two "shells".

**Fix.** Only an instance started on a directory is the shell; one started on a `.qml` entry
file is a window (`pickShellInstance` in `desktop/cmd/zenith/ipc.go`).

**Evidence.** `TestPickShellInstanceIgnoresSecondaryWindows` builds the process table the
units and wrappers really produce. Without the filter the Hub's `hub.qml` makes the second
Zenith tree and the answer is "several Zenith trees are running, and refusing to guess".

## `~/.local/bin` is not on the PATH the shell runs with

**Symptom.** None seen yet; found by inspection before it bit. A script that runs from a
terminal would do nothing when the shell or a keybind started it.

**Cause.** The shell is a `systemd --user` unit. The user manager builds its own PATH, and
`~/.local/bin` is added by the login shell's profile, which the manager never reads.

**Fix.** Every script the QML or the compositor configuration calls by bare name is installed
into `/usr/bin` (the `release/build.d/*.build` lists), and `tests/contract/commands.py` fails
on a bare command that no build list, dependency list or allowlist accounts for.

**Evidence.** `systemctl --user show-environment` prints
`PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin`,
while the terminal's PATH starts with `/home/mohit/.local/bin`.

## The brightness keys need logind, not membership of `video`

**Symptom.** A write to the laptop panel's backlight was refused with a permission error, so
the brightness keys and sliders could not change it.

**Cause.** `/sys/class/backlight/intel_backlight/brightness` is `root:video`, mode `0664`,
and the account is not in `video`. Ubuntu's `brightnessctl` is built without logind support,
so its write is refused too (`docs/hardware-keys.md`). `docs/architecture.md` had declined the
udev rule that would fix this and left the display section with no slider.

**Fix.** `zenith brightness` asks logind to write the value
(`org.freedesktop.login1.Session.SetBrightness`), which the active session may do without
privilege, then falls back to `brightnessctl`, then to the sysfs file if it is writable. The
keys, the daemon and the sliders all go through it. No group change and no udev rule were
needed, so the boundary did not move.

**Evidence.** `ls -l /sys/class/backlight/intel_backlight/brightness` prints
`-rw-rw-r-- 1 root video`. `id -nG` for the account prints
`mohit adm cdrom sudo dip plugdev users lpadmin lxd docker ollama`, with no `video`.
`ldd /usr/bin/brightnessctl` (0.5.1-3.1build1) links no libsystemd, so it has no logind path.
